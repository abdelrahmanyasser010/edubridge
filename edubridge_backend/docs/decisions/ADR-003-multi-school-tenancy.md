# ADR-003: تعدد المدارس وعزل البيانات

- الحالة: Superseded by `ADR-007-database-per-tenant.md`
- التاريخ: 2026-07-12
- Task: DEC-002

## القرار

نستخدم Shared Database / Shared Schema. كل سجل مملوك لمدرسة يحمل `school_id` إجباريًا، وتكون العلاقات والقيود الفريدة والفهارس مركبة معه حيث يلزم.

## تحديد المدرسة الحالية

- المستخدم يرتبط بالمدرسة عبر `school_user` بعضوية لها حالة وفترة صلاحية.
- الحساب الإداري العام فقط يمكنه العمل عبر مدارس، ويختار مدرسة نشطة بصلاحية صريحة.
- تطبيقات المعلم وولي الأمر تستمد المدرسة من العضوية الموثقة، لا من `school_id` يرسله العميل.
- integration credentials مرتبطة بمدرسة واحدة ما لم ينص scope صراحة على غير ذلك.

## Enforcement

1. Middleware يبني `TenantContext` من المستخدم/credential الموثق.
2. إنشاء السجلات يملأ `school_id` من السياق، وليس من request body.
3. Queries وroute binding مقيدة بالمدرسة الحالية.
4. Policies تتحقق من المدرسة ثم علاقة المستخدم بالمورد.
5. jobs/events تحمل `school_id` و`correlation_id` صراحة وتعيد تهيئة السياق.
6. أوامر console التي تعالج بيانات مدرسة تتطلب school argument أو iteration صريحًا.

## استثناءات الجداول العامة

الجداول العامة المسموحة مبدئيًا: `users`, `schools`, تعريفات `permissions` النظامية، وجداول framework التقنية. ملفات الأشخاص وبيانات الدراسة والحضور والمال والإشعارات كلها school-owned.

## الاختبارات الإلزامية

- كل Feature API test حساس يثبت أن مستخدم المدرسة A لا يقرأ أو يعدل مورد المدرسة B حتى لو عرف ID.
- factories تنشئ المدرسة صراحة ولا تعتمد على default عالمي مخفي.
- unique constraints المحلية مثل code تتضمن `school_id`.

## بدائل مرفوضة الآن

- قاعدة منفصلة لكل مدرسة: تزيد إدارة migrations والنسخ الاحتياطية قبل وجود متطلبات عزل تنظيمي تفرضها.
- مدرسة واحدة hard-coded: تمنع التوسع وتزيد احتمال اختلاط السياق لاحقًا.
